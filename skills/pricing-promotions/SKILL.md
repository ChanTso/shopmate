# 价格草案与操作员批准

工具只准备草案、读取和取消。实际改价由操作员在工作台点击批准按钮，由 Java 事务校验并整批写入。聊天里的“批准”、模型自己的同意或推断都不构成批准。

## 准备前

- 先用目录工具找到实际商品，并读取 `get_listing`／`get_pricing_context`。商品名称有歧义时澄清，不凭简称猜 ID。
- `attributes.price_editable` 为 true 才可调价。普通商品须已发布、available，并且没有任何秒杀活动关联；CLOSED 或过期活动仍不满足条件。
- 一个草案最多 3 个不同商品且币种一致。超过范围先和用户缩小范围，不悄悄拆成多份以绕过一批审批。
- 用户给目标价就照目标价；用户给比例时以工具刚返回的当前标价计算，不用历史成交均价。CNY／USD 最多两位小数；遇到需要舍入但用户没有明确目标价的情况，先给出候选分币价请其确认，不静默截断金额。
- 不猜成本、毛利、需求信号或价格调整必然带来的经营效果；没有这些输入就保持缺失。价格上下限和变化比例不从旧演示商店规则继承。

## 生成与修订

- 调用 `stage_price_update` 时只传真实 listing_id 与确定的新价，可附简短业务说明。Java 冻结旧价、目标价和商品版本；会话、身份与请求幂等键由宿主提供，不能由模型指定。
- 成功返回的卡片已经是预览。简短说明草案已准备、仍待操作员批准，并准确区分现价和提案价；不要宣称已改价。
- 用户修改已准备的方案时，先 `discard_change` 取消旧草案，再创建新草案。旧草案保留旧参数；不原地改写，也不先批准旧价再做第二次调价。
- 多份草案并存时，用工具返回的 change_id 对应各自商品与参数；分别取消或等待批准，不把对象混在一起。
- 网络中断后先通过 `get_pending_changes` 恢复未确定的 prepare 结果。不要为了找回结果重复发新的意图。宿主会用已持久化的原请求键恢复 Java 草案。

## 批准与读回

- `apply_change` 不在模型工具范围内。操作员批准后，查询实际商品和工作台记录的 receipt 再说明结果，不把“提交了草案”当成功改价。
- Java 的 APPLIED 表示整批应用；REJECTED 表示整批未执行，说明返回的业务原因；CANCELLED 表示取消；PREPARED 表示仍待审。不要把拒绝和取消混为一谈。
- `get_pending_changes` 只列仍待审的草案；已应用的结果以宿主操作回执及重新读取的商品为准。已经应用的草案不能再取消，需明确说明其真实状态。
- 不提供定时促销、优惠券、活动价、广告、库存或采购操作。用户只要求保留方案时，保持 PREPARED 就是完成目标。
