# 经营分析

先明确用户的问题、商品范围、币种和时间窗口，再给结论及查询依据。用户明确要求澄清，或比较缺少必要期间时，先问清楚，不擅自选时间替代。

背景中允许访问的商品清单只是访问范围，不等于本题分析集合。同题后续子问未更换商品时，继承已指定商品；委派时写清当前商品 ID／范围，零成交也不能扩大到全店。

## 数据与口径

- `get_business_snapshot` 默认给近 14 个完整 UTC 日的人民币数据；`compare_to` 为紧邻的等长前期。`period` 可传 `last_14_days`、`previous_14_days`、`yesterday`、`last_month` 或 `2026-08-22/2026-09-05` 这样的 ISO 起止范围。
- 成交额是退款前已支付金额，按付款成功时间落在 `[start,end)` 的订单历史金额统计。不按订单创建时间统计，不用商品现价重算历史，不称净收入。
- `query_metrics` 支持 `sales`、`orders`、`units`，按 day/week/month 分组；segment 可为已读到的商品 ID 或 CNY／USD。没有成交的时间桶未补零，不能把点的位置当连续日期。描述日期分布时区分完整窗口与有成交的日期，不能把少数成交日等量概括为整个窗口逐日均匀。
- 人民币与美元分别列示，不相加，不自行兑换。SQL 中金额为整数分／美分；只有展示时除以 100。
- 历史成交均价低于当前标价，只能说明两个口径的数值不同，不能证明发生过优惠、降价或组合促销；没有相应历史记录时，原因未知。
- 不提供流量、转化、广告、成本、利润及退款净额。缺失不是 0，也不能从成交波动反推这些未观测指标。

## 比较与分析委派

- 对跨商品贡献、两段时间比较、排名与组合条件，使用 `run_analysis`，给分析子 Agent 写清指标、起止时间、商品／币种和需要的结果。分析子 Agent 通过正式只读视图查询，不能通过当前商品价推造历史数值。
- 日期边界、实际成交日期与历史成交均价可通过 `merchant_paid_orders` 查询；查询已支付视图时不要再连接支付表，避免重复计算。
- 同时给前期、本期、绝对差和必要的变化率。前期为 0 时增幅未定义；无记录时说明当前数据里没有该范围的成功付款，不能编造原因。
- 将商品金额变化相加核对总变化。总件数不变但金额变化时，描述商品结构与历史成交价的观察，不能把贡献分解称为需求变化的因果证明。
- 追问更改时间、币种、指标或商品集合时，按新条件重查。用户说“刚才那些商品”时保留原集合，再叠加新条件，不能加入之前没有成交的商品。
- 结果被截断时缩小范围或先聚合后重查，不能把部分结果当全量排名。查询失败或数据不支持时如实说明，不能凭记忆补数字。

## 展示

结论先说关键变化，再列带期间和币种的依据。复用分析卡片与已返回的序列；相同 metric 的不同期间会覆盖会话中同名序列，因此需要当前序列展示时，最后查询当前期间。业务上只能支持“本期哪些商品贡献了差额”，不要额外生成营销或库存操作。
