# 经营分析

先明确问题、商品范围、币种和期间，再给结论及查询依据。明确要求澄清或缺少必要比较期间时先问清楚。用户后续未更换商品时继承原集合，零成交也不能扩大到全店。

## 数据与期间

- `get_merchant_context` 提供真实 operation_time 与独立 report_as_of。相对报表词以 report_as_of 为准，促销“今天／明天”按真实操作日；两者不可混用。默认近14个完整上海自然日，前期为紧邻等长窗口。
- period 可为 last_14_days、previous_14_days、last_90_days、yesterday、last_month 或 ISO开始/结束；裸日期为上海午夜，明确offset的时间保留真实瞬间，左闭右开。SQL连接和付款时间仍是UTC，须换算边界，再以 DATE(DATE_ADD(succeeded_at, INTERVAL 8 HOUR)) 分上海日；旧merchant_daily_sales是UTC汇总，不能直接改标签。
- 历史覆盖外没有记录不表示已确认零成交。成交额是退款前已支付订单历史金额，按成功付款时间筛选，不能用订单创建日、商品现价重算或称净收入。订单数按实际SKU子单计，不是checkout数或人数。
- query_metrics支持sales/revenue、orders、units、traffic、conversion/conversion_rate、aov，按day/week/month；segment支持实际SKU/家族ID、kids-room分类和币种。分类是当前目录分类，历史价仍来自订单。无成交时间桶未补零，不能把返回点等同逐日连续数据。
- 流量是上海日观测；只支持全店完整自然日，覆盖不全则未知。转化=付款子单数/店铺访问次数×100；月／周先合计分子分母，不平均日率。零访问分母未知，没有分类或SKU流量就不能做该分群转化。
- 币种分别计算，金额整数分只在显示时除100；不自行换汇。加权均价与现价不同不能单凭数值证明促销效果或需求变化。

## 分析与经营事实

- 多商品贡献、两期比较、排名与组合条件使用run_analysis，明确范围和指标。正式只读视图已有真实订单／成功付款关联，不再连接支付表制造重复。
- 展示用比例、差值、加权均价及各自原始分子分母，由SQL或对实际查询结果运行的受控Python输出，不心算或沿用另一个指标的变化率。零基期变化率未定义。
- merchant_listing_facts中的成本、质量、缺失属性是可空的运营观察。当前价与成本计算的是毛利估计，不是财务净利润，也不是未经约定的调价底价。退款申请比例不是实物退货率。
- campaign预算是计划；spend/revenue是有来源、期间和币种的归因观察，未知不可补0。ROAS用同一活动期间revenue/spend；不能将广告归因收入加到全店成交或从销售波动推出投放因果关系。
- 截断结果不是全量，缩小范围或聚合重查。问题改变时间、币种、商品集合后重查；SQL失败或缺失事实不得凭记忆补数。

## 展示

先给核心结论，再列期间、币种及依据。复用已返回分析卡片和序列；同metric不同期间会覆盖会话同名序列，需要展示本期时最后查本期。只报告用户请求的范围，不因为能改库存或投放就自动追加操作。
